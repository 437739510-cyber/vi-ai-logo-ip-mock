# Brand Brain 本地 Codex 工单工作模式（总控大脑 + 执行手）

> 版本：1.0
> 日期：2026-08-02
> 依据：`HANDOFF-BB-LOCAL-BRAIN-2026-08-02.md`（第 3、4、5、6、7、8、9、12、13、17 节）
> 适用：本仓库任何 Codex 实例（主窗 / 侧窗 / 子代理）处理工单时统一遵循

---

## 0. 一句话原则

主窗是“大脑与监理”，执行手是“唯一写代码的人”。一张工单配一个执行手；
只有主窗正式评审 `PASS` 之后，才能另开独立检查点工单谈提交。

---

## 1. 角色分工

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| 总控大脑（主窗） | 只读调查、写工单、派生执行手、核对 diff/测试/Git、判定 PASS/HOLD/BLOCKED | 不亲自写代码、不连续堆积执行内容 |
| 执行手（worker 子代理或侧窗） | 按工单调查→修改→定向测试→完整回归→Git 自检→写回执→验证回执 | 不扩权、不提交、不部署、不付费 |
| 只读调查/评审子代理 | 并行核查调用链、断言、diff | 不并行修改代码 |
| Chris | 决定优先级与方向、最终授权提交/推送/部署/付费 | 不逐句搬运命令 |

同一时间只允许**一个写代码的执行手**。可并行多个只读调查，禁止两个执行手同时改同一工作区。

---

## 2. 工单必备要素（缺一不可）

1. 工单编号与性质
2. 真实项目路径
3. 当前基线核验（分支、HEAD、origin/master 本地引用、git status --short）
4. 目标与非目标
5. 根因或待取证问题
6. 允许修改的文件白名单
7. 禁止事项
8. 必须保留的合法能力
9. 执行步骤
10. 测试命令与精确预期（数量、退出码）
11. 停止条件
12. 回执路径与必填内容
13. Git 最终状态要求

---

## 3. 标准闭环流程

```text
Chris 提出目标
    ↓
主窗读取全局状态并做只读调查、判断根因与修改边界
    ↓
主窗写一张完整工单（按第 2 节 13 项）
    ↓
主窗派生一个 worker 子代理（Chris 在场且要求可见侧窗时，给完整工单由 Chris 开侧窗）
    ↓
执行手连续执行：调查 → 修改 → 定向测试 → 完整回归 → Git 自检 → 回执写盘 → 回执验证
    ↓
主窗收回执行摘要，亲自核对真实 diff、测试退出码、回执与 Git 状态
    ↓
判定 PASS / HOLD / BLOCKED（必要时先派生只读 reviewer 复核）
    ↓
PASS 后才另开“本地检查点”独立工单；暂存与提交需再次明确授权
    ↓
不 push、不部署（除非 Chris 另行授权）
```

不得把“整改通过”和“允许提交”混在同一张工单里。

---

## 4. 执行手默认禁止事项

除非当前工单明确授权，否则一律禁止：

- `git add`、`git commit`、`git push`、`git pull`、`git fetch`
- merge / rebase / reset / stash / checkout 覆盖
- 创建 PR、部署、远端写入
- 付费 API 调用、读取或输出 secrets
- 删除用户文件、覆盖用户已有改动
- 修改工单白名单之外的文件
- 放宽、删除或伪造测试断言
- 启动/停止 Worker、ComfyUI、本地服务器、定时 watcher
- 把 `logs/` 或启动时已有未跟踪内容纳入变更或清理

默认执行方式：本地、离线、零付费。

---

## 5. 主窗评审必查证据

测试全绿不等于实现正确。至少核对：

- `git diff --stat`、`git diff --name-only`
- `git status --short`、`git diff --cached --name-status`（应为空）
- 与根因有关的实际 diff
- 测试命令、退出码、失败行；断言数量与强度未被削弱
- 测试输入层级与生产调用链一致（不拿中文夹具掩盖英文传参问题等）
- 回执文件存在性、大小、NUL 数、UTF-8 BOM、SHA256（工单要求时）
- 所有改动文件是否仍在白名单内，`logs/` 是否未被纳入

## 6. 工单状态机

| 状态 | 含义 |
| --- | --- |
| `DRAFT` | 主窗正在调查和拟定工单 |
| `ISSUED` | 工单已交给新执行手 |
| `RUNNING` | 执行手正在实际执行 |
| `REVIEW` | 执行手完成，等待主窗正式评审 |
| `HOLD` | 表面通过但证据或实现存在问题，不得提交 |
| `BLOCKED` | 命中停止条件，需要主窗或 Chris 决策 |
| `PASS` | 正式评审通过，可考虑独立检查点工单 |
| `CHECKPOINTED` | 已按独立授权创建本地提交（不代表已 push/部署） |
| `CLOSED` | 本轮目标完成并完成必要交接 |

主窗每次答复都应明确：当前工单编号 + 状态。

---

## 7. 无人值守三级机制

### 第一级：工单内自动闭环

派生执行手时必须要求：除明确停止条件外，持续执行到调查、修改、定向测试、完整回归、
Git 自检、回执写盘和回执验证全部完成；不得停在“准备检查”“下一步”等说明文字；
必须输出真实命令、真实结果和退出码。

### 第二级：Goal 模式

长工单在主窗启用 Goal，目标必须包含：当前唯一工单编号、完成结果、修改白名单、
禁止事项、验收命令、停止条件、最终状态必须为 PASS/HOLD/BLOCKED 之一。

### 第三级：守护心跳（每 10 分钟）

当前工单手动运行稳定后，在主聊天内创建每 10 分钟一次的守护心跳，只守护当前已授权工单。

每次心跳执行：

1. 读取当前聊天中的工单编号、白名单、停止条件和验收标准；
2. 检查当前 worker 子代理是否仍在运行；
3. 若仍在运行，只记录状态并等待，不启动第二个写入代理；
4. 若 worker 已完成，收回结果，核对回执、`git diff --stat`、`git diff --name-only`、`git status --short`、`git diff --cached --name-status` 和工单要求的测试证据；
5. 若只缺少当前工单明确要求的安全验收，向原 worker 发补充指令并继续等待；
6. 必要时可派生只读 reviewer 复核调用链、断言和 diff，但不得并行修改代码；
7. 最终由主窗判定 PASS、HOLD 或 BLOCKED；
8. 达到终态后不再修改代码，不自动进入下一工单，不 commit、不 push、不部署；支持自动暂停则暂停，否则后续心跳只报告“当前工单已终止，等待 Chris”；
9. 命中扩权、冲突、付费、远端、密钥、删除、提交、部署或产品决策时，立即判定 BLOCKED 并等待 Chris；
10. 全程保持 `logs/` 与启动时已有用户改动不受影响。

心跳不获得任何新授权，只能在当前工单已有授权范围内行动。

---

## 8. 执行手必须停止的条件

命中以下任一情况必须停止并报告阻塞事实、证据、影响、建议选项，不得自行扩权：

- 需要修改白名单之外的文件
- 发现用户已有改动与工单冲突
- 需要远端、付费、登录或密钥操作
- 需要删除、覆盖或重置内容
- 基线与工单显著不一致
- 真实测试数量或调用链与工单假设冲突
- 无法证明修复没有削弱测试
- 需要产品决策而非单纯工程修复

---

## 9. 标准回执模板要点

`REPORT-<工单编号>.md` 至少包含：

1. 结论（完成 / 阻塞 / 未通过）+ 是否满足工单目标
2. 启动基线（时间、仓库、分支、HEAD、origin/master、git status --short、暂存区）
3. 调查证据与根因（生产调用链、失败复现）
4. 实际修改表（文件 / 修改理由 / 是否在白名单）
5. 风险与保留能力（未削弱的能力、未放宽的断言、未触碰的范围）
6. 验证结果表（检查项 / 命令 / 结果 / 退出码）
7. Git 自检（diff --check、--stat、--name-only、status --short、cached --name-status）
8. 安全确认（未 add/commit/push、未部署、未远端或付费、logs/ 未纳入）
9. 回执文件验证（EXISTS、PATH、SIZE_BYTES、NUL_COUNT、UTF8_BOM、SHA256）

---

## 10. 完成标准（对每张工单）

1. 根因已在可复用的平台逻辑中修复
2. 通用回归场景通过，且没有削弱断言
3. 原有相关 PASS 没有退化
4. diff 仅包含授权文件，没有行尾噪声
5. 报告列出实际运行的测试、结果/退出码、剩余失败，以及是否发生 commit、push、部署、进程启停、远端写入或付费调用

---

## 11. 伪修复黑名单

禁止以下做法：

- 删除失败断言或放宽关键词/判定范围
- 对输出做测试后处理
- 针对测试品牌/项目写特殊分支
- 用静态中文文案覆盖动态语义问题
- 只让 smoke 通过而不核对生产调用链
- 在 Renderer、Planner、Worker 各自复制不同规则（应建立 SSOT）

---

## 12. 给其他 Codex 实例的使用说明

- Chris 说“开一张工单 / 派执行手”：按第 3 节流程，先只读接管核验基线，再派生 worker 并交付完整工单。
- Chris 直接粘贴工单：按第 4、8、9 节执行与自审，命中停止条件才停下报告。
- Chris 说“看看为什么 / 评审 / 分析”：只做只读调查和结论，不自动实施修复。
- Chris 说“修好 / 实现 / 继续整改”：主窗才可开实现工单。
- 提交、推送、部署、付费、扩白名单：永远需要 Chris 在当前工单中明确授权。

## 13. 本机 worker 运行模式（2026-08-02 实证版）

本机硬件实测：Intel i5-4460（4 核 4 线程，无超线程）、16 GB 内存、
RTX 3060 12 GB 显存（当前基本闲置）、D 盘空闲 1 TB。以下模式基于
2026-08-02 四个 worker 子代理的实际表现总结。

### 13.1 已知现象（实证）

- 初始派发消息（spawn 时一次性交付）可靠；`followup_task` 的补充消息内容
  在本机多次丢失（worker 只回“等待工单”或模板话术）。
- 大而全的长工单容易长时间空转（无落盘修改、无消息）；子代理再派生子代理
  基本必然卡死（worker1 观察 2 小时无产出）。
- worker3 证明：一个自包含的中等工单可以由 worker 本人完成（约 40 分钟），
  但同一 worker 无法可靠接收后续补充指令。

### 13.2 本机 worker 使用规则

1. **小任务优先**：一张 worker 工单只做一件事（改一个文件 / 跑一组测试 /
   写一份回执）。大任务拆成连续的小工单，主窗逐个派发、逐个回收。
2. **双通道交付**：完整工单同时放在 spawn 消息 与 `_bridge/` 文件中，
   并在工单开头要求 worker 先回复一行“工单已收到”作为送达证明。
3. **快速止损**：派发后若 5 分钟无送达确认、或 20 分钟无任何落盘修改，
   中断并重新派发，不无限等待。
4. **禁止子代理**：worker 一律不得再派生子代理。
5. **禁止 followup 依赖**：后续修正必须作为新工单文件（写入 `_bridge/`）
   或新 worker 的初始消息交付，不依赖 followup_task 内容送达。
6. **重活串行**：tsc、完整回归、smoke、PPTX 渲染一次只跑一个；只读调查
   用定向 rg/按文件读取，禁止全仓库递归扫描。
7. **机器空闲时跑**：CPU 负载高于 60% 或空闲内存低于 4 GB 时，推迟重活；
   显卡（ComfyUI/Ollama）与 tsc/回归不同时运行。
8. **验收必由主窗复核**：worker 报告全绿不等于通过，主窗必须亲自核对
   diff、退出码、断言数量和回执哈希后再判定。

### 13.3 显卡用途（12 GB 显存）

- 主线：本地 ComfyUI（`comfyui-workflows/` 已有中文 Logo / 公仔三视图 /
  场景工作流），worker.mjs 已内置对接，一次一个生成任务。
- 辅助：Ollama 本地模型供 worker 做离线草稿 / 归类 / 抽取，零付费；
  不作为 Codex 本体推理引擎（Codex 运行在云端模型上）。
- 纪律：生成任务在机器空闲时运行；开工前查显存与内存余量。

### 13.4 本机首选执行通道（2026-08-02 实证结论）

内置 worker 子代理在本机不可靠（5 次尝试仅 1 次完整跑通，消息送达与长任务
空转问题反复出现）。因此首选执行通道为：

1. **主窗开工单**（按第 2 节 13 项要素），Chris 新开一个可见的 bb-clean
   侧窗口粘贴执行；
2. **一窗一工单**：一个侧窗只做一张工单，闭环后写回执即结束，不叠加第二张；
3. **修正不走内置消息通道**：需要修正时，主窗输出完整修正版工单给新侧窗，
   或对很小的修正由主窗直接完成；
4. **主窗只评审不代劳**：判定前必须亲自核对实际 diff、测试退出码、
   断言数量与回执哈希；测试全绿不等于通过。

内置 worker 子代理仅保留给两类任务：已确认送达的只读调查小任务，
以及 Chris 明确要求“无人值守”时的尝试性执行（按 13.2 的快速止损规则）。

### 13.5 本地检查点默认化（2026-08-03 Chris 决策）

- Chris 已确认：本地检查点有好处，**以后每张实现工单正式评审 PASS 后，默认进入
  “本地检查点”流程**：主窗把白名单文件精准暂存 → 核对 staged diff 与密钥 → 创建
  本地 commit（不 push、不部署、不建 PR）→ 登记 CHECKPOINTED。
- 唯一例外：Chris 在当次工单明确表示“暂缓检查点”时，才跳过并等待指示。
- 检查点 commit 只包含当张工单白名单文件；工作模式文档、logs/、_bridge/ 等
  不混入实现工单的检查点。

### 13.6 工单立项权限（2026-08-03 Chris 决策）

- **质量相关改动**（会影响客户对手册质量/满意度的功能，如“人工改色入口”等）：
  必须先问 Chris 是否要做，得到确认后才能开实现工单。
- **遗留清单清理**（审计确认的低优先技术债、死代码、过时注释、小优化）：
  Chris 已授权主窗自行安排清理，不用逐项询问；但每项清理仍走完整工单 →
  侧窗执行 → 主窗评审 → 本地检查点流程。

### 15. 产品规则备忘（2026-08-03 Chris 口头确认）

- **场景图行业一致性**：场景图必须与客户行业匹配——例如餐馆的场景图应是
  “含 LOGO 的餐巾纸/餐具”，绝不能出现“含 LOGO 洗车液”等跨行业画面。
- 对应保障点：
  1. 场景提示词必须以行业（industryType）与行业知识为准生成（worker
     buildScenePrompts / getIndustryKnowledge 链路）；
  2. 场景图内容的最终校验需要**视觉评审**（本机规则：DeepSeek 不能看图，
     需授权后调 TokenHub hy-vision 或由 Chris 人工确认），文字/XML 核验
     只能证明物料卡正确，不能证明图片内容正确。

### 16. 场景图“沐浴乳”根因结论（2026-08-03 排查）

- 现象：奶茶店测试单场景图出现沐浴乳（跨行业画面）。
- 根因：**提示词管线问题，非生图模型不稳定**。DeepSeek 已生成行业正确的
  sceneImageSuggestions（奶茶杯/杯套/茶罐/招牌/海报），但 worker.mjs 第 496 行
  使用通用模板 buildScenePrompts（“产品包装盒”等，未指定产品），未消费
  DeepSeek 的行业提示词 → Z-Image 自由发挥画出沐浴乳。
- 行业分类本身正确（饮品→beverage、快餐→fastfood）。
- 修复：worker 优先使用 brandProfile.sceneImageSuggestions（注入品牌名），
  缺失才回退通用模板（工单 021）。
